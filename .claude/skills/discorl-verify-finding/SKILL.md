# Verify a cda-discorl finding before it costs anything

Most of this package only does something inside RLlib's Learner, so a claim read off the source
is often wrong about what runs. Reproduce first.

## Steps

1. **State the claim as a scenario**: which settings block, which module, which hook
   (`build`, `_policy_value_loss`, a connector, `apply_gradients`, `get_state`/`set_state`), and
   what wrong value or crash results.
2. **Reproduce it in the scratchpad**, not in the repo. Two levels, cheapest first:
   - `validate` and pure functions: call them directly, for example
     `config.validate({**config.DEFAULTS, ...}, TrainConfig(**TINY))` with `TINY` from
     `tests/conftest.py`.
   - Anything on the Learner: build a tiny real run, as `RealRun` does:
     `build_config(train_config(settings, seed=7))[0].build_algo()`, then inspect
     `algo.learner_group._learner` (its `_learner_connector.connectors`, the module via
     `learner.module[mid].unwrapped()`, and `algo.train()["learners"][mid]` for metrics).
     Start Ray with `num_cpus=3` and `include_dashboard=False`; set `OMP_NUM_THREADS=1`.
3. **Run the inverse** (a case that should pass) so the repro can tell the two apart.
4. **Check reachability.** Can a train config produce that state? gym-CDA rejects unknown keys
   before `validate`; `num_learners > 1` is refused for stateful components; `disco103` refuses
   three components; `lstm` is refused for `policy_prediction` and `disco103`.
5. **Check which repo owns it.** A gym-CDA seam (`_policy_value_loss`, `extra_trunk_heads`,
   `moe_learner._collect`), the `disco_rl` fork (never edited here) or cda_cbp's resets may be the
   real owner. File it there, or as a decision for a person.
6. **Classify**: confirmed, false positive, unreachable, already tracked, or cannot reproduce.
   Search the open issues first (`gh api -X GET search/issues -f q='repo:ChuaCheowHuan/cda_disco_rl <words>'`);
   if it is tracked, comment there instead of filing a duplicate.

## Filing a confirmed finding

- Labels: a severity (`S1-blocking` .. `S4-minor`), a kind (`bug`, `enhancement`,
  `documentation`, `test-gap`, `refactor`), and `agent` (an AI agent can resolve it from the
  issue alone) or `human` (needs a decision, credentials, a research call or another
  maintainer). Needs both: split into sub-issues, one label each (`parent_issue_number`).
- Set the issue type (Bug, Task or Feature) with the issue tool's `type` parameter.
- Put the repro and its output in the body, with the versions (`ray`, `torch`, `jax`, gym-CDA
  commit). End with `_Generated by [Claude Code](https://claude.ai/code)_`.

## Guardrails

- Report false positives to the user with the reason; do not drop them silently.
- In a review, do not fix: file. Fix only when asked, test first (CLAUDE.md rule 4).
